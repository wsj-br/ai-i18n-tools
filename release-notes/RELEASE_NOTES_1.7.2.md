# ai-i18n-tools 1.7.2 Release Notes

## Highlights

- **Self-localized tool UI:** The CLI help, high-traffic log/summary/error messages, and the Translation Dashboard now render in a UI locale resolved (high → low priority) from the global `-L, --ui-lang <code>` flag, the `AI_I18N_LANG` environment variable, the new config `uiLanguage` key, then the host OS locale, falling back to the source locale (`en-GB`) when nothing matches. A lightweight `t()` runtime keyed by the English source string powers it, and the tool's own bundles are dogfooded through the extract → `translate-ui` pipeline. When an explicitly requested UI language has no shipped bundle, the CLI prints a one-time warning that the default locale will be used.
- **HTML `data-i18n` extraction and the new `mark-html` command:** `extract` can now capture UI strings directly from `.html` / `.htm` sources via `data-i18n`, `data-i18n-title`, and `data-i18n-placeholder` markers (bare markers take the source text from the element itself; `data-i18n-ignore` skips a subtree). The new `mark-html [paths...]` command auto-inserts those markers (dry run by default; `--write` applies atomically) without calling an LLM. The scanned attributes are configurable via `ui.uiExtractor.htmlI18nAttributes`.
- **Dashboard localized from its own HTML:** The dashboard frontend is fully localized, with all static markup annotated via `data-i18n*` markers and strings now extracted straight from `index.html` (the manual `i18n-registry.js` mirror was removed).
- **Accurate token & cost accounting:** Interrupting a document-translation run (`Ctrl-C`) no longer reports `Total tokens used: 0` after batches had already succeeded, and tokens/cost spent on billed-but-discarded LLM responses (empty content, parse failures, wrong-script output that later fell back to another model) are now folded into run totals instead of being dropped.
- **Smarter wrong-script validation:** Output-script validation now uses a statistical dominant-script check (ignoring Latin code/URLs/brand names and letter-like symbols such as `ℹ`) instead of rejecting a whole completion on the first stray character, removing false positives. It also adds real Simplified-vs-Traditional (`zh-Hans` vs `zh-Hant`) discrimination via a vendored Han-variant character set, with safeguards against false positives on ordinary Traditional text and short segments.
- **Stricter locale validation:** Script-ambiguous bare subtags (e.g. `pa`, `zh`) that only have regional/script variants in the catalog are now rejected with a helpful "did you mean …?" hint instead of being silently degraded to placeholder rows.

## Why this release matters

Version 1.7.2 makes ai-i18n-tools speak your language — the CLI, logs, and dashboard now localize themselves — and adds first-class HTML string extraction (plus a `mark-html` helper). It also makes translation runs more trustworthy: token/cost totals stay accurate through interrupts and discarded responses, and wrong-script detection (including Simplified vs Traditional Chinese) is far less prone to false positives.

## Detailed Changes

- **Added**: cli/i18n — when the tool's UI language is explicitly requested via `-L, --ui-lang`, the `AI_I18N_LANG` environment variable, or config `uiLanguage` but no shipped bundle matches (the resolver falls back to the source locale), the CLI now prints a one-time yellow warning that the default locale will be used (`initUiI18nFromEnvironment` in `src/i18n/index.ts`). The warning is intentionally not routed through `t()` (it always renders in the default/source language, since the requested locale is unavailable). A locale inferred only from the host OS never triggers a warning, and the warning is de-duplicated per requested value so the startup + post-config resolution passes do not warn twice.
- **Added**: extractors — HTML `data-i18n*` marker extraction. A new `src/extractors/html-i18n-marks.ts` scanner lets `extract` capture UI strings from `.html` / `.htm` sources (when listed in `ui.uiExtractor.extensions`) via `data-i18n` (element `textContent`), `data-i18n-title`, and `data-i18n-placeholder` attributes. Bare markers take the source text from the element itself (no duplication); valued markers (`data-i18n="Key"`) set an explicit key for mixed content. `data-i18n-ignore` skips an element and its subtree. The shared `normalizeI18nText` helper keeps build-time keys identical to the browser runtime. Exposed from the public API (`collectHtmlI18nStrings`, `collectHtmlI18nLocations`, `markHtmlContent`, `normalizeI18nText`, …).
- **Added**: cli — new `mark-html [paths...]` command that auto-inserts bare `data-i18n` / `data-i18n-title` / `data-i18n-placeholder` markers into HTML (`src/cli/mark-html.ts`). Dry run by default (reports per-file add counts and mixed-content elements needing a manual `<span data-i18n>`); `--write` applies changes via atomic writes. Idempotent, honours `data-i18n-ignore`, never marks code-like elements (`code`, `pre`, `kbd`, `samp`, `var`) or empty / numeric-only text, and never emits a valued marker. Does not call an LLM.
- **Added**: config — optional `ui.uiExtractor.htmlI18nAttributes` (`src/core/types.ts`) to customize the scanned HTML marker attributes (defaults to `["data-i18n", "data-i18n-title", "data-i18n-placeholder"]`; `data-i18n-<attr>` maps to that attribute's value).
- **Changed**: dashboard — `src/dashboard-app/index.html` migrated to bare `data-i18n*` markers (mixed-content hints wrapped in `<span data-i18n>`, brand link and footer marked `data-i18n-ignore`), and `applyStaticI18n` in `src/dashboard-app/app.js` now derives the catalog key from the element's own `textContent` / `title` / `placeholder` (normalized) when the marker is bare. `ai-i18n-self.config.json` adds `.html` to `ui.uiExtractor.extensions` so `extract` captures the dashboard strings directly.
- **Removed**: dashboard — deleted `src/dashboard-app/i18n-registry.js` (the manual mirror of HTML strings as `t()` calls). HTML strings are now extracted from `index.html` markers, so the registry's `strings.json` entries keep the same hashes but their `locations` reference `src/dashboard-app/index.html`.
- **Fixed**: cli — corrected grammar/spelling in user-facing CLI strings flagged by `lint-source`: the "all files skipped" hint in `src/cli/index.ts` now reads `translation cache` (was `translationcache`) with a single space after the emoji, the `translate-svg` description drops a stray double space (`Translate  SVG` → `Translate SVG`), the `check-models` expired-models header shows `Past expiration date` instead of the raw `expiration_date` identifier, and the `write-heading-ids` log line is capitalized (`  wrote {{path}}` → `  Wrote {{path}}`). Source-text-keyed catalog entries change, so these keys re-translate on the next self-localization run.
- **Changed**: cli/format — the `printModelsTryInOrder` header prefixes (`Provider:` and `Models (try in order):`) in `src/cli/format.ts` are now localized via `t()` instead of printed as hardcoded English, so the `translate-ui` / `translate-docs` / `translate-svg` model banner respects the active UI locale. The labels are translated at print time (`t("Provider:") + " "`, `t("Models (try in order):") + " "`) and the models line wrapping width now uses the localized prefix length; the trailing separator space is kept outside `t()` because extraction trims catalog/bundle keys. The now-unused `PROVIDER_LOG_PREFIX` / `MODELS_TRY_ORDER_LOG_PREFIX` exports were removed (the prefix length is computed inline where needed).
- **Added**: cli — the CLI now auto-loads a `.env` from the current working directory at startup via `loadDotenv` (`src/utils/load-dotenv.ts`), so provider API keys (e.g. `OPENROUTER_API_KEY`) are picked up in non-interactive shells that do not source `.envrc`/`direnv` (such as agent-run commands). Uses Node's `process.loadEnvFile` (Node ≥ 22.16) and never overrides variables already set in the environment, so real CI/production values still win.
- **Added**: cli/i18n — self-localization of the tool's own UI. CLI help text, high-traffic log/summary/error messages, and the Translation Dashboard now render in a UI locale resolved from (high → low priority) the global `-L, --ui-lang <code>` flag, the `AI_I18N_LANG` environment variable, the new config `uiLanguage` key, then the host OS locale (`Intl.DateTimeFormat().resolvedOptions().locale`). Resolution (`resolveUiLocale` in `src/core/ui-locale.ts`) normalizes the candidate, matches it against the shipped locale set exactly or by closest variation (e.g. `pt-PT` → `pt-BR`, `en-US` → `en-GB`), and falls back to the source locale (`en-GB`) when nothing matches. A lightweight runtime (`src/i18n/`) provides `t(source, vars)` with `{{name}}` interpolation against flat per-locale bundles (`dist/i18n/locales/<code>.json`), keyed by the English source string; missing keys/bundles return the source text. The CLI resolves the locale before help is built (pre-parse argv scan) and re-resolves after config load so config `uiLanguage` applies (CLI/env still win).
- **Added**: config — optional top-level `uiLanguage` (BCP-47 string) controls the tool's own UI language (CLI logs, help, dashboard). It is independent of `sourceLocale` / `targetLocales`; unknown values degrade gracefully to the source locale (no strict validation).
- **Added**: server/dashboard — `GET /api/ui-i18n` returns `{ locale, dir, bundle }` for the resolved UI locale. The `dashboard` command passes the resolved locale, layout direction, and flat bundle; the frontend (`src/dashboard-app/app.js`) fetches it on load, sets `<html lang>`/`dir`, and localizes static markup via `data-i18n` / `data-i18n-title` / `data-i18n-placeholder` attributes.
- **Added**: utils/table — `src/utils/table.ts` (`displayWidth`, `padEndDisplay`, `padStartDisplay`, `renderTable`) computes terminal column widths via `get-east-asian-width` (CJK/emoji aware). The `status`, `statistics`, and `list-languages` tables now use display-width padding so localized headers/cells stay aligned in the console and `--write-logs` tee.
- **Added**: build — `ai-i18n-self.config.json` plus the `i18n:self` script (`ai-i18n-tools -c ai-i18n-self.config.json sync-ui`) dogfood the extract → translate-ui pipeline to produce the tool's own bundles under `src/i18n/locales`; `scripts/copy-i18n-locales.mjs` ships them to `dist/i18n/locales` during `build`.
- **Changed**: cli/i18n — extended self-localization `t()` coverage beyond `src/cli/index.ts` to the remaining CLI command modules (`doc-translate.ts`, `translate-ui-strings.ts`, `translate-svg.ts`, `check-models.ts`, `list-models.ts`, `list-languages.ts`, `lint-source.ts`, `translate-json-run.ts`, `extract-strings.ts`, `check-markdown.ts`, `write-heading-ids.ts`, `clean-temp.ts`, `format.ts`, `export-ui-xliff.ts`, `generate-ui-languages.ts`, `openrouter-catalog-model-filter.ts`, `doc-translate-quality-retry.ts`), so their progress/summary/error console output is now translatable. Dynamic error strings (`e instanceof Error ? e.message : String(e)`) and non-prose tokens (paths, model ids, config keys, CLI commands) are intentionally left untranslated.
- **Fixed**: cli/i18n — wrapped the remaining hardcoded user-facing strings in `src/cli/index.ts` so they reach the catalog and localize. Every subcommand `.option()` / `.argument()` description and the `--max-columns` validator messages are now passed through `t()` (only literal value enumerations like `markdown | json` and `github | bitbucket | …` stay English), and the leftover `console.*` / `throw` prose (cache-stats labels, `--force`/`--force-update` conflict blocks, `clear-cache` messages, the docs[] progress header counts, the `status` JSON legend + `Locales N–M of T` chunk labels, the `statistics` `(no locale rows)` line, and all `[cleanup]` log lines) is wrapped with `{{…}}` placeholders. Catch-block error prefixes (`❌ [scope] {{error}}`) are now localized consistently with `translate-ui`. Command names, option flags, and dynamic tokens (paths, locales, model ids) remain hardcoded.
- **Changed**: dashboard — completed localization of the dashboard frontend. `src/dashboard-app/index.html` now annotates all static text (hints, table headers, filter placeholders/titles, option labels, buttons, modal titles, and the server-down overlay) with `data-i18n` / `data-i18n-title` / `data-i18n-placeholder`, and the remaining dynamic strings in `src/dashboard-app/app.js` are wrapped in the existing `t()`. (HTML-only source strings are now captured directly from `index.html` by `extract` — see the bare-marker entry above.)
- **Added**: tests/utils — added full unit coverage for `loadDotenv` (`src/utils/load-dotenv.ts`): the no-`.env` no-op, loading new variables from a temp-dir `.env`, never overriding a pre-existing `process.env` value, and the warning paths for a missing `process.loadEnvFile` and for `Error`/non-`Error` load failures.
- **Added**: tests/i18n — substantially expanded unit coverage of the self-localization runtime (`src/i18n/index.ts`, now ~100% statements/lines), exercising `loadUiManifest` (including a mocked unreadable/non-source manifest), `availableUiLocales`, `uiLocaleDirection` (ltr default and a mocked rtl locale), `loadUiBundle` (source/empty/missing/invalid-JSON/array shapes), `readUiLangFromArgv` (all flag forms), `resolveUiI18n` / `initUiI18nFrom`, and `initUiI18nFromEnvironment` (argv > env > config precedence).
- **Fixed**: tests/i18n — corrected the stale `ui-i18n-runtime` assertion that assumed no shipped `de.json` bundle; with the dogfooded bundles now present, `t("Save")` under `de` is asserted to return the translated `Speichern` (with an unknown key still falling back to source).
- **Fixed**: extractors/cli — several CLI help strings stayed in English under a non-source UI locale. (1) The UI-string extractor (`firstArgStringLiteral` in `src/extractors/ui-string-babel.ts`) now also captures `t(`…`)` template literals that have no `${}` interpolation, so the multi-line root help footer (`More detail:` …) and every `Examples:` block are added to the catalog and translated; literals embedding expressions are still skipped. (2) Those `t(`…`)` call sites in `src/cli/index.ts` now keep their surrounding blank lines outside `t()` (the extractor trims catalog keys, so a leading/trailing newline would never match at runtime). (3) Commander's built-in `output the version number` and `display help for command` descriptions, plus the default `Options:` / `Commands:` group headings, are now registered as catalog keys and localized at render time in `formatCliHelp`.
- **Fixed**: cli/docs — interrupting a document-translation run (`Ctrl-C`) no longer reports `Total tokens used: 0` / `Total cost: $0.0000 (all segments from cache)` after batches had already succeeded. Completed API spend was only added to the live summary (`liveSum`) once an entire file finished via `recordFileTotals`; on interrupt the in-flight file threw (and `runMapWithConcurrency` rejects, discarding completed batch results) before that ran, so all spent tokens/cost were dropped. `LlmClient` now takes an `onApiUsage` sink that fires the instant each billed response arrives in `fetchCompletion` (including responses later discarded), and `runTranslate` (`src/cli/doc-translate.ts`) wires it to accrue `liveSum` tokens/cost directly (with `accumulateFileTotals(..., { skipUsage: true })` so completed files are not double-counted). The summary's cost line now gates on actual API work (tokens/cost) instead of `segmentsTranslated`, so an interrupted run with no fully-completed file still prints the real spend.
- **Fixed**: api/llm-client — tokens and cost spent on billed-but-discarded LLM responses are no longer dropped from run totals. When a provider (e.g. OpenRouter) returns a charged response that is then rejected — empty content, batch parse failure, or wrong-script output — and a later model in the fallback chain succeeds, that wasted `usage`/`cost` is now folded into the successful result's totals (`chat`, `translateDocumentSegment`, `translateDocumentBatch`, `translateUIBatch`, `lintUISourceBatch`, `translatePluralCardinalBatch` in `src/api/llm-client.ts`), so reported total tokens/cost reflect every charged call. When every model fails, `DocumentBatchAllModelsFailedError` now carries the discarded `wastedUsage`/`wastedCost`. Empty-content rejections now throw an internal `BilledCompletionError` so their usage is accounted for instead of silently lost.
- **Fixed**: api/llm-client — output-script validation now uses a statistical dominant-script check instead of rejecting a whole completion on the first non-expected letter. `assertExpectedScript` (`src/api/llm-client.ts`) calls the new `scriptValidationIssue` (`src/core/locale-utils.ts`), which ignores Latin letters (code, URLs, brand names, placeholders) and Common/Inherited characters — including letter-like symbols such as `ℹ` (U+2139) that match `\p{L}` — so a stray foreign-language quote or an info/arrow glyph no longer trips the check (it must take more than 60%, `EXPECTED_SCRIPT_MIN_SHARE`, of the meaningful letters to be flagged). This removes the `contains characters outside the expected … script (ℹ)` false positives seen on `zh-Hans` / `zh-Hant` document runs.
- **Added**: api/llm-client — real Simplified-vs-Traditional (`zh-Hans` vs `zh-Hant`) discrimination. Unicode has no Simplified/Traditional script property (both are `Han`), so a new vendored character set (`src/core/han-variant-data.ts`, MIT-licensed data from `traditional-or-simplified`; regenerate with `scripts/gen-han-variant-data.mjs`) powers `hanVariantCounts`; `scriptValidationIssue` now rejects a `zh-Hant` output that is predominantly Simplified (and vice-versa) while leaving shared-only Han text untouched. New `scriptLetterCounts`, `hanVariantCounts`, `scriptValidationIssue`, and `EXPECTED_SCRIPT_MIN_SHARE` are re-exported from `config` and the package root; `disallowedScriptLetters` / `nonLatinLettersIn` are retained for back-compat but are no longer used by the validator.
- **Fixed**: core/locale-utils — the Simplified-vs-Traditional check no longer raises false positives on Traditional output. (1) Characters the upstream list mislabels as Simplified-only but that are used unchanged in both writing systems (`面`, `制`, `里`, `系`, `范`, …) are excluded from `SIMPLIFIED_ONLY`/`TRADITIONAL_ONLY` (`VARIANT_AMBIGUOUS` in `src/core/han-variant-data.ts`), so ordinary Traditional words like `界面`/`控制`/`系統` are no longer counted as Simplified. (2) `scriptValidationIssue` now requires at least `VARIANT_MIN_SAMPLE` (4) variant-distinct characters and flags only when the wrong variant is a clear majority (> 60%), so a tie or a one/two-character segment is never rejected (previously a 1-vs-1 tie reported `predominantly Simplified Chinese (50% …)`).
- **Changed**: core/prompts — the `zh-Hans` / `zh-Hant` script directive now appends an explicit character-form clause (`Use Simplified … NEVER Traditional forms`, and vice-versa, with examples) to steer weaker models toward the correct variant.
- **Fixed**: config — locale validation (`assertEffectiveLocalesInUiLanguagesMaster` in `src/core/ui-languages-catalog.ts`) now requires an exact match in the bundled catalog (`data/ui-languages-complete.json`), the same rule `buildUiLanguageRowsFromMaster` uses to build the manifest. Previously a script-ambiguous bare subtag with only regional/script variants in the catalog (e.g. `pa` → `pa-IN`/`pa-PK`, `zh` → `zh-Hans`/`zh-Hant`) passed validation and was then silently degraded to a placeholder row at build time (`No master entry for locale "pa"; using placeholders`). Such tags are now rejected with a `ConfigValidationError` like any other unknown locale, and the error suggests the available variants (`did you mean "pa-IN" or "pa-PK"?`). Bare subtags that have an exact catalog entry (`en`, `pt`, `fr`, …) are unaffected.
